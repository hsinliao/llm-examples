你给的每一轮输入，就是模型能看到的全部世界。它没有记忆、不会主动追问、只会顺着你给的文本往下接。所以提示词的本质不是“咒语”，而是把任务交代清楚。
下面六条建议，每条都对应一个你已经理解的机制。

一、先给角色和任务，再给问题
模型是“预测下一个 Token”的，开头几个词会强烈影响后续走向。先告诉它你是谁、要干什么、按什么标准，比直接抛问题稳定得多。
差：这个报错怎么解决？
好：你是一个 Java 后端工程师。下面是一段 Spring Boot 启动报错，请先判断根因，再给修复步骤，不要贴大段无关代码。报错如下：...
角色和约束放在最前面，等于给整段回答定了“基调”。


二、要什么格式，直接说；能给例子，就给例子
模型不会读心。你要表格就给表头，要 JSON 就给字段名，要三点结论就说“分三点”。给一个输入输出示例，比描述十句格式要求都管用——因为模型是在模仿你给的模式往下接。

差：帮我整理一下这些信息。
好：把下面的信息整理成表格，三列：问题、原因、建议。示例：| 启动慢 | 依赖过多 | 按需引入 starter |

三、有材料就直接贴，别让它“回忆”
这是 RAG 思维的日常版。模型的知识有截止时间，也不了解你的私有内容。与其问“我们公司的退款规则是什么”，不如把规则原文贴进去，再问“按这段规则，这个订单能不能退”。
日常用 AI 时，凡是涉及具体文档、具体数据、具体代码，第一反应应该是“我把它贴进去”，而不是“它应该知道”。贴材料时加一句“只根据以上材料回答，材料里没有就说不知道”，能显著减少编造。

四、复杂任务拆步骤，别一口气全塞
上下文窗口有限，任务越复杂，模型越容易漏掉中间约束。把“分析 + 决策 + 输出”拆成几轮，每轮只让它做一件事，比一段超长 Prompt 更可靠。
比如写方案：第一轮让它列提纲，你改完；第二轮按提纲填内容；第三轮让它自查逻辑漏洞。每轮你都能纠偏，而不是等它一口气写完发现方向错了。
这也对应 Agent 的思路：分步、可检查、每步有明确产出。

五、明确说“不要什么”，比只说“要什么”更有效
模型倾向于“多给”，你不限制，它就长篇大论。长度、语气、禁忌都要显式说：
回答控制在 200 字以内，不要分点，不要用“首先其次最后”，不要重复我的问题。
尤其是“材料里没有就说不知道”、“不确定的地方标注出来” 这类约束，能直接压住幻觉。

六、它没有记忆，追问时要带上文
你感觉它在“对话”，其实是你的客户端每次把历史重发了一遍。所以：
换新会话 = 失忆，重要背景要重新给；
长对话到后面它开始“忘事”，不是它变笨，是早期内容被挤出窗口了——这时把关键结论重新贴一遍，比反复追问有效；
同一个问题答案不一样是正常的（采样有随机性），要稳定就要求它“先给结论再给理由”，并降低发散。

一个日常可用的模板
把上面几条收成一个顺手就能套的骨架：
【角色】你是……
【任务】请完成……
【材料】以下是相关资料：……
【要求】输出格式为……；不超过……字；材料中没有的不要编；不确定的标注“待确认”。
【示例】（可选）输入……输出……

最后一条务实建议：不要追求“完美提示词”。
提示词是迭代出来的——先给一版，看输出哪里不对，针对不对的地方补一句约束，再跑一遍。
你每补的一句约束，本质上都是在缩小“下一个 Token”的候选空间。这比背模板有用得多。
