把 Demo 推进到生产，心态上要先做一个根本转变：不要把它当成“调用一个聪明的函数”，而是当成“调用一个昂贵、不可靠、还会自作主张的远程服务”。
一个真实的教训是：有团队上线了订单查询 Agent，用户问“查一下昨天退款失败的订单”，模型理解成了“把昨天退款失败的订单重新退一遍”，万幸工具方法里加了幂等校验才没出事。
生产级的健壮性，就是围绕这个认知，把 LLM 纳入你已有的工程治理框架

架构原则：把 LLM 当作“不可靠 RPC”来设计
普通 RPC 调用你有超时、重试、降级、幂等这套底牌，但 LLM 抽走了其中三张：
无会话：它不记得任何东西，“对话历史”是你每次请求重新拼上去的。
非确定性：同样的输入，温度调到 0 也不保证同样的输出。
有副作用：工具调用可能真的执行了操作（下单、退款、发邮件），不是只返回一个结果。
这意味着你的架构必须比普通 RPC 更保守：所有工具方法默认加幂等校验，所有 LLM 调用默认加超时和熔断，所有输出默认经过校验再放行。
弹性与容错：超时、重试、熔断、降级
LangChain4j 的同步调用有内置重试循环，但流式路径默认没有重试——一次 429 或 5xx 会直接抛到应用层。所以不能依赖框架默认值，需要在 AiServices 外层或模型构建时显式治理。
分层超时是基础：连接超时、读取超时、整体调用超时分开设置。读取超时要能覆盖慢模型的长输出，但整体超时要有一个硬上限，防止 Agent 循环卡死。
重试只对幂等操作开放：对于纯查询、翻译、摘要这类无副作用的调用，可以重试；对于涉及工具调用的 Agent 请求，重试必须极其谨慎，因为模型可能在第一次“超时”时已经执行了工具。一个务实的做法是：在工具方法内部做幂等（唯一键、版本号），而不是在调用层盲目重试。
熔断和降级要内建到调用链里。目标不是“LLM 挂了整体不可用”，而是“LLM 挂了客服系统还能给出兜底回复”。可以用 Resilience4j 或 Spring Retry 包裹 AI 服务调用，错误率超过阈值时快速失败，进入降级路径（返回缓存答案、静态话术或转人工）。
Quarkus 生态提供了注解式的 @Retry、@Timeout、@RateLimit、@CircuitBreaker 组合，Spring 侧则需要自己组合 Resilience4j 的装饰器。

多模型路由与故障转移：别把鸡蛋放在一个篮子里
生产环境不能假设单一模型供应商永远可用。LangChain4j 社区提供了 ModelRouter，内置两种策略：

FailoverStrategy 按注册顺序发送消息，第一个模型失败立即切到下一个，并对失败模型设置冷却期（默认 1 分钟）后再重试。配置大致如下：

ModelRouter router = ModelRouter.builder()
        .addRoutes(primaryModel, secondaryModel)
        .routingStrategy(new FailoverStrategy(Duration.ofMinutes(5)))
        .build();

需要注意：FailoverStrategy 会把失败模型的异常隐藏掉，调用方感知不到切换发生了；如果需要追踪，必须注册 error listener。
LowestTokenUsageRoutingStrategy 则把请求发给累计 Token 消耗最少的模型，适合成本敏感的批量任务。
更进一步，你可以实现自定义 ModelRoutingStrategy，根据消息长度做路由：短消息走便宜的小模型，长消息走上下文窗口更大的模型。这正是“路由优先”的成本控制思路：用便宜模型能解决的问题，不要交给贵模型。
安全与护栏：Guardrails 不是可选项
LangChain4j 的 dev.langchain4j.guardrails 包提供了输入和输出的验证机制。
输入护栏的核心职责是防提示注入。官方提供了基于 OWASP LLM01 模式的 PromptInjectionGuardrail，用正则检测并阻断注入尝试。但正则只能拦住已知模式，更强的方案是用一个独立的 DecisionModel 做判断，让一个小模型专门回答“这段输入是否试图改变系统指令”。更工程化的做法是把确定性策略（正则）和模型判断串联：正则先过一遍低成本的硬规则，模型再做语义层面的判断，两层都通过才放行。
输出护栏同样重要。如果你的业务依赖结构化输出（JSON 响应、枚举值、特定格式），不能信任模型“会按格式来”。LangChain4j 提供了 OutputGuardrail 来校验响应能否成功反序列化为目标类型。对于非结构化的文本输出，至少要加内容合规审核（ModerationModel）和业务规则校验（比如“不得包含内部订单号”）。
护栏的位置应该在 AiServices 的调用链上，作为装饰器包裹原始调用，而不是散落在业务代码里。

可观测性：没有它，生产问题就是黑盒
LLM 调用最贵、最慢、最不可预测，如果不观测，你连“钱花在哪了”都不知道。LangChain4j 生态提供了 OpenTelemetry 集成，核心指标和追踪会自动生成：
langchain4j.aiservices.timed：AI 方法执行耗时 Timer；
langchain4j.aiservices.counted：调用次数 Counter；
追踪 span：langchain4j.aiservices.$interface.$method 和 langchain4j.tools.$tool，覆盖 AI 服务调用和工具执行。
Token 用量必须作为一等指标暴露。Telemetry 模块已经在 span 中记录了输入/输出/总 Token 数。在这个基础上，你可以按模型、按接口、按租户维度聚合，做配额和成本归因。如果使用 AWS Bedrock，Prompt Caching 的命中率和缓存 TTL 也应该一并监控。

在 Spring Boot 中，如果官方 telemetry 模块覆盖不到你的场景（比如你用了自定义的 ChatModel 包装），可以用装饰器模式手动包裹 ChatModel 和 Tool，在装饰器里打点并上报 OTel。
性能与成本：缓存、流式、上下文预算
缓存是 ROI 最高的优化。对高频相似问题缓存 LLM 响应，经验上可以降低 40–60% 的成本。缓存键不能只用原始问题字符串，应该用规范化后的语义表示（去除无意义变体、提取核心意图），或者直接用问题的 Embedding 做近似匹配。Redis 或 Caffeine 都可以做存储层。
流式输出是用户体验问题，不是成本问题——它不改变总 Token 数，但能让用户更早看到内容。流式场景的关键风险是背压缺失：模型每秒产出 20–100 Token，如果消费者侧的审核、日志、WebSocket 广播处理不过来，积压会撑爆缓冲区甚至导致内存泄漏。LangChain4j 的 TokenStream 实现了 Iterable，可以配合 Project Reactor 做“拉”模型消费；较新版本还提供了 toFlowPublisher() 接入 JDK Flow 背压协议。不要在 onPartialResponse 回调里做重操作，把非关键逻辑移到流结束后异步处理。
上下文预算管理直接对应你之前理解的“上下文窗口有限”。MessageWindowChatMemory 只保留最近 N 条消息；更进一步可以用摘要模式：把早期对话压缩成一段摘要，而不是直接丢弃，Token 成本可以再降 20–40%。Agent 场景尤其要注意，工具定义的 JSON Schema 本身也占 Token，工具多时不应该一次性全量注入。
测试与评估：确定性测试覆盖不了 LLM
传统单元测试在这里不够用，因为输出是非确定性的。生产级实践需要评测集驱动迭代：维护一组“问题–期望行为”的样本，每次修改 Prompt、更换模型、调整检索策略后，跑一遍评测集，观察通过率是否回退。

评测集至少覆盖三类场景：正常路径（应该正确回答）、边界条件（信息不足时应该拒答而不是编造）、对抗输入（提示注入、越权指令）。对于 Agent，还要评估工具选择的正确性和参数填充的准确性，而不只是最终回答的文本质量。
